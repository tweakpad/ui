## Usage

The value is a flow document, `{ version: 1, nodes, edges }`, where each node names a `type` from the schema, a `position` and its `data`, and each edge connects a `source` node and port to a `target` node and port. `schema` describes the node types, their ports and the control each property shows; it is a property, so it is always set from script, along with `icons` when definitions name icons. `load(document)` replaces the document, and `default-value` (JSON) or `defaultValue` seeds an uncontrolled instance.

The widget fills its container's inline size and needs a block size: give it one directly, as these examples do, or let it fill a sized parent. Its canvas never gets shorter than the size's minimum (30rem by default, 22.5rem at `size="sm"`), so keep the block size at least that tall. Drag nodes to move them, drag from a port to another port to connect, scroll or pinch to pan and zoom, and press <Keys keys="delete" /> to remove the selection; <Keys keys="mod+z" /> undoes any of it.

`size="sm"` tightens the node width, ports, handles and the intrinsic height.

`tp-flow` is part of `@tweakpad/ui/register/widgets`. The separate `@tweakpad/ui/flow` entry is the DOM-free engine (`parseFlowDocument`, `serializeFlowDocument`, `validateDocument`, `layoutFlow`, `FlowModel` and the routing and run helpers). Apps do not need it to render a flow; import it when the same documents are validated, laid out or migrated in a worker or on a server.

Routing and layout can leave the main thread. In a Worker, build a `FlowModel` from the document, create a planner with `createRoutingPlanner(model, options)`, run it in slices (`run(budgetMs)` returns `{ done, routed, remaining, elapsed }` and resumes where it stopped; `pending` stays true until routing and nudging are both finished) and send the routes back as typed arrays: `packRoutes(planner.routes.values())` packs ids, kinds, offsets, coordinates, flags, hashes, radii and stubs into transferable buffers, and `unpackRoutes(packed)` rebuilds the `FlowRoute` map on the other side. `layoutFlow(model, direction, options)` returns positions, sizes and the `changes` list; post the changes and apply them with `flow.propose(changes, 'layout')` followed by `flow.commit('layout')` so the lanes, the history and a controlled owner see one layout transaction.

### Schema and ports

A node definition sets `type`, `label`, `shape` (`card` by default, `compact`, `panel` or `group`), a `tone`, its `ports` and its `properties`. Ports have an `id`, a `direction` (`input` or `output`) and a `dataType`; a connection is refused when the types do not match, so the schema's `dataTypes` decide what may connect, and their tones paint the ports. `show-port-labels` shows each port's label beside it, which suits panel nodes where every row has its own port.

A release then dispatches the cancelable `tp-connect` with `{ connection, edge, reason, sourceEvent }` (a handler may change `detail.edge`, for instance its `kind` or `label`), proposes the `edge-add` with the reason `connect` and commits.

With `connectOnClick` (default) a click on a port starts a connection (`aria-pressed`) and a click on another port completes it. From the keyboard, Enter on a focused port starts a connection, arrows and Tab cycle the valid candidates (each announced), Enter confirms and Escape cancels. A selected edge has a reconnect anchor at each end `reconnectable` allows: an invisible grab area on the edge just beyond the socket (a move cursor), so the socket itself keeps starting new connections. Dragging an anchor re-targets the edge after the same validation (`metadata.reconnect: { edgeId, end }`); the old edge hides while dragging and comes back when the drop lands nowhere. A focused anchor shows its ring, and Enter or Space on it starts a keyboard reconnect: the arrows cycle the valid sockets (each announced), Enter or Space confirms and Escape cancels. `connect(connection, edge?)` and `reconnect(edgeId, end, connection)` do the same from code; `getNodeConnections(id)` lists a node's edges.

Properties name a `key` of the node data and a `control`: `slider`, `number`, `text`, `textarea`, `select`, `switch`, `checkbox`, `color` or `easing`, each rendered by the library component of that name. Editing a control inside a node proposes a change to the document like any other edit, so it can be undone.

`propertyControls` replaces any of them (and must supply `custom`): a factory `(context) => TemplateResult` receives `{ node, definition, value, disabled, readOnly, propose, commit, port, id }` and renders a control that proposes through `propose(value, reason)` and settles with `commit(reason)`. A node whose type has no definition renders as a card with the shape's default size and no ports.

### Edge kinds

An edge's `kind` is `smoothstep` (the default), `bezier`, `step`, `straight` or `orthogonal`; `rules.defaultEdgeKind` sets it for new connections. `animated` marches a dashed stroke from source to target so the direction reads at a glance, and adds a closed arrow that keeps it readable when reduced motion pauses the dash. `label` renders as a Badge pill on the path.

`markerStart` and `markerEnd` take `arrow`, `arrowclosed`, `circle`, `diamond` or a definition `{ type, width, height, color, strokeWidth, orient, units }`; markers are defined once per flow and paint with the edge's stroke. `label` is a shorthand for `labels: [{ text }]`; each label sits at `position` (0–1 along the path, 0.5 by default) with `align` and `placement` (`on`, `above`, `below`) and renders as an outline Badge pill. `edgeTemplates`, keyed by edge id or kind, replaces the label content with a template `(context) => TemplateResult` over `{ edge, kind, selected, label }`.

Each edge has a 20 px invisible hit path: a click selects it, hovering marks it, a double press on a segment adds a waypoint there (`track-press`), and `waypoints` are must-pass points the path visits in order: a `straight` edge becomes a polyline through them, `step` and `smoothstep` an axis-aligned path with their corners that leaves and enters along the port sides, a `bezier` a smooth curve, and routed edges route through them (`edgePathThrough` in the engine). A selected edge shows its waypoint handles (focusable; arrows nudge, Delete removes) and, on a routed (orthogonal) path, a handle on each interior segment that moves the segment along its normal while the rest re-routes (the segments at the sockets stay put); both produce `edge-waypoints` changes. The handles sit above the paths, sockets and labels, and a press released without moving only selects a handle: the selected handle (the one a press or the keyboard last focused) wears the active ring and is what Delete and the arrows act on. Delete removes a selected waypoint and selects the next one (else the previous one); with none left, focus returns to the selected edge. Edges take focus through hidden proxies (`E` cycles the focused node's edges, `focusEdge(id)` from code) and Delete removes the focused or selected edges.

### Declarative nodes

Nodes and edges can be written as `tp-flow-node` and `tp-flow-edge` children. They are adopted into the document by `id`; `x` and `y` place a node, `data` is JSON, and an edge takes `source`, `source-port`, `target`, `target-port`, `kind`, `label`, `animated` and `marker-end`. Dragging writes back only the `x`, `y`, `width` and `height` attributes. Content inside a node renders in its body, and a library control with `data-flow-property` edits that key of the node data.

### Node library and inspector

`palette` adds the node library: `palette` alone (or `palette="sidebar"`) floats a sidebar at the inline start, and `palette="menu"` opens a Dialog of columns. The schema's `categories` group the definitions. Open it with the floating "+" Toggle, then drag a chip onto the canvas, or click it and then click where the node should go. `default-palette-open` starts it open.

- `sidebar`: a bar floating over the canvas at the inline start, on the same surface and inset as the inspector, its width set by the size axis, with a "Node library" header and a Close Button (Escape closes it too). Under the search an Accordion section per group (several may be open; `open` of the category sets the start) lists the definitions; while searching, the matching groups replace the sections. It stays open after an insertion; the panels at the inline start move clear of it, and fitting the view centers the graph in the canvas it leaves uncovered.
- `menu`: an "Add node" Dialog modal to the widget over a blurred backdrop (container modality: the canvas behind it is inert, Escape and its Close Button close it) whose groups lay out as columns under their headings, wrapping to further rows when they do not fit. It closes after an insertion and focus moves to the new node.
- Library items: each definition is a compact outline Button chip with its icon and label (the description, or `strings.dragToPlace`, as its tooltip) under the toned heading of its group; the search filters by label, description, type and group. Chips are dragged onto the canvas and a drop inserts the node centered on the drop point; the menu turns transparent while a chip is dragged, so the whole canvas takes the drop, and comes back when the drag is cancelled. A click on a chip arms placement instead, the single-pointer alternative to dragging: the pane shows a copy cursor, the live region reads `strings.announcePlacing`, the next press on the pane places the node there and Escape cancels. Enter or Space on a focused chip inserts at the center of the uncovered canvas. With a pending anchor (the "+" of an edge label or the point of a released connection) any activation inserts there and connects. An insertion proposes with `metadata.insert: { type, at }` and selects the new node.

The inspector holds settings the schema places off the node with `placement: "inspector"`; compact nodes keep all their properties there. With `inspector="auto"` (the default) a double press on such a node opens it, as on "Paid orders" here, and it then follows the selection. `inspector-commit="explicit"` holds edits until Save.

### Controls, minimap and panels

`controls` lists the actions of the built-in toolbar in order: `zoom-in zoom-out fit tool undo redo lock` by default, with `zoom` (a zoom field), `layout` and `run` available on request and `controls=""` for no toolbar. `controls-position` and `controls-orientation` place it. The bar is one tab stop: its controls, the node library Toggle and the zoom field's menu trigger included, are reached with the arrow keys. In a vertical bar, ArrowDown and ArrowUp on the zoom trigger open its menu, so list `zoom` last or reach the controls after it with Home and End. `minimap` adds an overview in `minimap-position`, and `background` draws `dots`, `lines`, `cross` or `none`.

The built-in bar takes `controls`, `controls-position` and `controls-orientation`; `zoom` is the zoom field: the current level (type a percentage and press Enter) and a menu of fit (Shift+1) and preset levels (100% is Shift+0).

Panels anchor to the corners and edge middles (`top-start`, `top-center`, `top-end`, `center-start`, `center-end`, `bottom-start`, `bottom-center`, `bottom-end`). A `tp-flow-controls` child slotted into one is another standard bar the widget keeps in sync; Buttons inside it join its keyboard navigation. Any other slotted content is a panel of your own.

`pushRunEvent(event)` feeds a live run one event at a time: the first event starts a live player on the current graph, which follows later edits (added nodes join idle, removed ones leave). `clearRun()`, or `run = null`, clears it.

- `node_progress` reports a fraction from 0 to 1 and an optional `message`; `node_waiting` a `reason` (an approval, an external system); `node_warning` a `message` that does not fail the node. Warnings accumulate until the node starts again.
- `run_started` with `scope: string[]` is a partial run: only those nodes reset, the others keep their earlier results, and the end of the run marks unreached and cancelled nodes inside the scope only. `run_failed` keeps its `error` on the run.

Node statuses (`idle`, `pending`, `running`, `waiting`, `success`, `failed`, `skipped`, `cancelled`) show in the status footer: a Spinner or a Marker, the detail and a status Badge. `default-value` or `defaultValue` is what Reset restores.

### Nodes

Shapes come from the definition: `card` composes a Card with an icon tile, the title, the description and a status footer (the workflow monitor); `compact` is an icon tile with a caption (pipelines); `panel` is a Card with a toned header and List item rows of label and control, each row's port aligned with it (material and shader graphs); `group` is a dashed, resizable container with a label whose children are positioned relative to it. Before measurement a node takes its definition's `size`, else the shape default: card 240 × 96, compact 96 × 68, panel 220 × 160, group 320 × 240. Measurement follows the rendered box and the port positions; a persisted `size` comes from a resize or a declaration.

`nodeTemplates` replaces the body per type: a template `(context) => TemplateResult` receives `{ node, definition, selected, dragging, lod, status, ports(side), control(key) }` and renders what it likes, calling `ports('left')` for the port elements of a side and `control('retries')` for the library control bound to a property. The host keeps the group role, the focus, the drag grip, the ports and the resizer.

Groups are nodes whose definition has `shape: 'group'`; membership is `parentId`, positions are parent-relative, `extent: 'parent'` keeps a child inside, a dragged child near the border expands the parent, deleting a group deletes its descendants and the dependent edges, and a child paints above its parent with the selection elevated.

A press on a node selects it (Shift adds, Command or Control toggles) and a drag moves every selected draggable node by the same delta, keeping the press offset, snapping to `snapGrid` when `snap` is on, clamped by the parent extent, auto-panning near the pane edge; the drag proposes once per frame and commits once on release. Escape restores the pre-drag positions (`escape-key`), a cancelled pointer restores them (`pointer`), and a lost capture settles at the last position. A selected resizable node shows the resizer: four focusable corner handles, the definition's `minSize` and `maxSize`, Shift keeping the aspect ratio, arrows resizing by a grid step and Escape restoring; the result is a `node-size` change. `pinned` keeps a node in place during automatic layout (the node toolbar and the context menu pin and unpin).

Only the nodes and edges inside the viewport plus an overscan margin have DOM: `virtualize` (default) pools `tp-flow-node` hosts and rebinds them as the view moves, unmeasured nodes are materialized until measured, the focused node stays materialized, and `visibleNodeIds` and `visibleEdgeIds` list the current set; `virtualize="false"` renders everything.

### Viewport

A left drag pans in the pan tool, while Space is held or with the middle button. `wheel` sets what a plain wheel does: `pan` (default), `zoom` toward the pointer, or `none` to leave the page's scrolling alone; Control or Command with the wheel (a trackpad pinch) always zooms toward the pointer and Shift swaps the axes. The wheel works anywhere over the canvas, nodes and panels included: a wheel over a node or panel goes to its content only when something there can scroll in that direction (a long list, a textarea), and otherwise moves the canvas. A wheel stream keeps the owner its first wheel chose, the way the browser latches native scrolling, so nodes that pan under a stationary pointer never stop it; the stream ends after a 500 ms pause, when the pointer moves more than 10 px, or when Control or Command changes. On touch, one finger on the empty pane pans in either tool and a second finger pinches around the midpoint (a touch press never starts a marquee); a double press on the empty pane zooms in by 1.2, and `cooperativeGestures` hands plain wheel and one-finger pane gestures to the page. Node, connection, marquee and resize drags auto-pan near the pane edges.

### Selection and editing

The selection lane is `{ nodes, edges }` (`tp-selection-change`): a press selects, Shift adds, Command or Control toggles, and a press on a control inside a node selects that node while the control keeps the press; in the select tool a press on the empty pane starts a marquee that selects nodes it touches (`selectionMode="partial"`) or encloses (`full`), Shift extends it, a press without movement clears, and Shift with a press in the pan tool also starts a marquee. Command or Control with A selects everything and Escape clears. `select({ nodes, edges })`, `selectAll()` and `clearSelection()` do the same from code; selection is never written into the document.

Copy, cut, paste and duplicate (`Mod+C`, `Mod+X`, `Mod+V`, `Mod+D`; `copy()`, `cut()`, `paste(payload?, { at })`, `duplicate()`) exchange `application/x-tweakpad-flow+json` with a JSON text fallback through the clipboard: a paste remaps ids, drops the nodes one grid step away or at the pointer, keeps the edges among them and selects what it pasted. Keys typed into an editable control inside a node stay with the control. `nudgeSelection(delta)` moves the selection by a delta; keyboard nudges coalesce into one history entry.

Undo and redo (`Mod+Z`, `Mod+Shift+Z`, the Undo and Redo controls; `undo()`, `redo()`, `canUndo`, `canRedo`) replay the engine's history: one entry per gesture, nudges coalesced, measurements, viewport and selection never recorded. `tp-history-change` reports every history change with `{ canUndo, canRedo, undoLabel?, redoLabel?, depth }` (the labels name the step, such as `move` or `connect`), so a consumer bar can enable its own buttons. Each step is proposed through the value lane with `metadata.history` set to `undo` or `redo`, so a controlled owner can veto it. Delete and Backspace, the node toolbar and the context menu delete the selection: the cancelable `tp-delete` carries the nodes (with their descendants) and the dependent edges, the deletion is one transaction, focus moves to the nearest remaining node, and `deletable: false` keeps an element out of it. Edge-only deletions, Cut and `deleteElements({ nodes, edges })` never ask; the method runs the deletion at once, after `tp-delete`.

The context menu is a Menu with the context invocation (right click, Shift+F10, the ContextMenu key, a long press). Its subject comes from the press: a node (or the selection it belongs to), an edge or the pane. A press anywhere outside the open menu, the canvas included, closes it and keeps its meaning (a press on the pane also clears the selection); a right press elsewhere moves the menu to the new subject. Pointer presses focus nodes without the keyboard focus ring. The default items are duplicate, copy, cut, pin or unpin (in automatic layout) and delete for a node (preceded by align left, align top, distribute horizontally and distribute vertically when two or more nodes are selected); add waypoint and delete for an edge; paste, select all, fit view and lay out for the pane. With `runnable`, Run node, Run from here and Run up to here lead the node items and Run graph the pane items. Each item carries its icon and, where a key binding exists, its shortcut as a Key hint (Mod+D, Mod+C, Mod+X, Mod+V, Mod+A, Shift+1, Backspace); delete is the destructive variant. `contextMenu(subject)` renders the items instead: `subject` is `{ kind: 'node', nodeId, selection }`, `{ kind: 'edge', edgeId, selection }` or `{ kind: 'pane', point, selection }`; items with the built-in values (`duplicate`, `copy`, `cut`, `delete`, `pin`, `unpin`, `align-left`, `align-top`, `distribute-x`, `distribute-y`, `add-waypoint`, `paste`, `select-all`, `fit`, `layout`, `run-node`, `run-from`, `run-to`, `run-graph`) keep their behavior, items with other values handle their own activation, and `contextMenu = false` removes the menu. A node with inspector settings gets a Settings item first (`settings`; it opens the inspector and focuses its first field). The node toolbar appears above a single selected node with Settings (only when the node has inspector settings), duplicate, pin (in automatic layout; pressed while pinned) and delete, led by Run node with `runnable` (which also shows the toolbar, with Run alone, when the widget is read-only or in view mode); `nodeToolbar(context)` renders its content from `{ node, definition }` and `nodeToolbar = false` hides it.

### Renderer

The widget resolves what to draw and a renderer draws it; the default SVG renderer keeps one `<svg>` per flow with a group per visible edge, and a WebGL renderer implements the same `FlowRenderer` interface:

  readonly capabilities: { edgeFocus: boolean };
  attach(host: FlowRenderHost): void;
  detach(): void;
  setViewport(viewport: FlowViewport): void;
  syncEdges(edges: readonly RenderedEdge[]): void; // the full visible set; diff by id
  setConnectionLine(line: ConnectionLineState | null): void;

On `attach` the host supplies the layer element to append to, the owner `window`, a per-instance `id` for marker names, the size, the pixel ratio, the viewport, the reduced-motion and forced-colors flags, `token(name)` to read a design token (`--tp-primary`) through the host's computed style and `requestRender()` to ask the widget for a pass; renderers never schedule frames or read globals themselves. Each `RenderedEdge` carries the edge, its kind, the resolved path (`points`, `d`, `bbox`, `center`, `length`), both endpoints, the stacking `z`, the `selected`, `hovered`, `focused`, `animated`, `routed` and `fallback` flags, the run `status`, the dash `direction`, the tone, the stroke width, the marker specs, the resolved labels and whether it is `interactive`.

### Constituents and accessibility

The root is an application region (`role="application"`) named by `label` ("Flow" by default) with a role description and the hidden instructions; it is `aria-busy` while the engine lays out. Each node is a group with the role description "node", named by `getNodeAriaLabel` or its label, definition label, run status and ", selected"; the nodes form one roving tab stop over the model order. Ports are native buttons named "Node: Port input" or "… output" with `aria-keyshortcuts` and `aria-pressed` while click-connecting. Edges are groups with the role description "edge" named "Edge from A to B, label", focusable through overlay proxies so focus works with every renderer. A polite live region announces moves ("Moved Send auto-reply to 700, 380"), connections, the candidate during a keyboard connection, deletions, the selection count, layout completion, the zoom level after a keyboard zoom and run transitions. Under reduced motion the dash flow, the viewport and layout tweens and the selection transitions are off; under forced colors the strokes use `CanvasText` and `Highlight` and every status keeps its text and icon. `strings` overrides every visible and accessible string (`FlowStrings`), `locale` formats the fields.

### Parts and customization

The composed Card of a node is registered as `flow-node-card`, its List item rows as `flow-node-row`, the toolbar Buttons and Toggles as `flow-control` and the node library's chips as `flow-palette-item`; `tp-flow-node` exports its parts, so `tp-flow::part(flow-node-title)` reaches rendered and authored nodes alike and `partPresentation` hooks reach the widget parts and the registered nested parts.

Every color resolves through tokens: the frame and the background through `--tp-background`, `--tp-foreground` and `--tp-border`, cards through the Card recipe, rows through List item, pills through Badge and Marker, ports, waypoints and handles through the shared thumb recipe painted with `--tp-primary`, edges through a foreground mix that turns `--tp-primary` when selected or focused, the marquee through a translucent `--tp-accent` fill with a dotted `--tp-primary` outline, run statuses through `--tp-warning` (pending, waiting), `--tp-primary` (running, active), `--tp-success` (success, taken), `--tp-destructive` (failed) and `--tp-muted-foreground` (skipped, cancelled, not taken, disabled), typed tones through `--tp-chart-1` to `--tp-chart-5` and the status tokens.
